# Preview Zoom And Pan Implementation Orchestrator

Status: execution runbook.

This file controls how to execute the phased implementation. It does not replace the authoritative implementation plan:

- Authoritative plan: `docs\preview-zoom-and-pan\preview-zoom-and-pan-implementation-plan.md`
- Resolved decisions record: `docs\preview-zoom-and-pan\preview-zoom-and-pan-open-questions.md`

If this runbook conflicts with `docs\preview-zoom-and-pan\preview-zoom-and-pan-implementation-plan.md`, the authoritative plan wins.

## 1. Execution Policy

- Implement this feature in the run order below.
- Do not begin a downstream run until every command, gate, and file-scope check in the current run passes.
- Passing agent-verifiable gates do not require human approval by default.
- If the user asks for full implementation, continue from one passing run to the next without waiting for approval, while still reporting each run summary.
- Human review blocks progress only under section 3.
- If a gate fails, patch only files allowed for the current run or revise the authoritative plan before touching additional files.
- Use `python -B` for tests and in-memory compile checks so validation does not write bytecode into the worktree.
- If validation creates or modifies `__pycache__/` or `.pyc` files, remove untracked generated bytecode or restore bytecode files modified by validation, then rerun the bytecode-free command.
- Do not modify geometry, KML/KMZ parsing, buffering, simplification, sectioning, JPG generation, KMZ export, output naming, cache-key semantics, dependencies, or launcher behavior.
- Do not modify `test_data/`, `outputs/`, launcher files, `agent_prompt_templates/`, or files in `C:\Users\rbake\Desktop\VS Code Shortcuts\Buffer-Zone-Generator`.
- Do not launch, attach to, automate, close, kill, inspect, script, or otherwise interact with any Agisoft Metashape process, window, project, task queue, or processing job.
- Do not read from, write to, copy, move, delete, lock, or otherwise touch Metashape project artifacts, including `.psx`, `.psz`, and `.files` project directories.
- Generated manual-validation files, if any, must be disposable and must not be written into `test_data/`, `outputs/`, source sample folders, or external reference repos.
- After every run, report changed files, commands run, pass/fail status, failures fixed, remaining risks, and whether the next run is safe to start.
- Every run must include both `git status --short` and `git diff --name-only` in its file-scope check.
- `git diff --name-only` does not show untracked files, so `git status --short` is mandatory.

## 2. Run Report And Continuation Policy

At the end of every run, provide:

- Run number and phases completed.
- Files changed.
- Tests and commands run.
- Pass/fail result for each command.
- Any failures fixed during the run.
- Any remaining risks or observations.
- Whether the next run is safe to start.

Continuation rules:

- If the current run passes and no human-blocking condition exists, the agent can proceed to the next run without waiting for user approval when the user has requested implementation to continue.
- Agent-performed manual validation does not require human approval unless the output is visually or semantically ambiguous under section 3.
- If the current run passes but the user requested only that run, stop after reporting.
- If the current run fails, do not proceed until the failure is fixed within the current run's allow-list or the authoritative plan is revised.

## 3. Human-Blocking Conditions

Human review or approval is required only when at least one condition below occurs:

- A required command fails and fixing it requires touching files outside the current run's allow-list.
- The implementation needs to revise the authoritative plan, file allow-list, product decisions, phase gates, or run grouping.
- The GUI cannot initialize in the available environment.
- Toolbar behavior cannot be verified from the available environment.
- Matplotlib's built-in toolbar cannot be embedded without adding a dependency or replacing the preview architecture.
- The implementation would require custom event handling beyond the resolved v1 toolbar decision.
- The implementation would alter geometry, export, simplification, sectioning, JPG generation, KML/KMZ parsing, cache-key behavior, dependencies, launcher files, or output naming.
- The implementation would modify `test_data/`, `outputs/`, launcher files, `agent_prompt_templates/`, Buffer-Zone-Generator, source sample folders, or Metashape artifacts.
- The implementation or validation would launch, inspect, attach to, script, interrupt, or otherwise interact with an active Metashape instance, project artifact, task queue, or processing job.
- Manual validation requires saving a toolbar image into a persistent or protected location.

No human review is required for:

- Passing unit tests.
- Passing in-memory source compile.
- Passing GUI smoke verification.
- Adding `NavigationToolbar2Tk` to the existing preview frame.
- Adding GUI tests for toolbar existence, toolbar layout, canvas layout, and empty redraw safety.
- Running disposable manual GUI validation without touching Metashape or protected folders.
- Updating optional validation notes under `docs\preview-zoom-and-pan\`.
