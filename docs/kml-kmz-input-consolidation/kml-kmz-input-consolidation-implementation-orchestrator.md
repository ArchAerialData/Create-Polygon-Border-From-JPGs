# KML/KMZ Input Consolidation Implementation Orchestrator

Status: execution runbook.

This file controls how to execute the phased implementation. It does not replace the authoritative implementation plan:

- Authoritative plan: `docs/kml-kmz-input-consolidation/kml-kmz-input-consolidation-implementation-plan.md`
- Resolved decisions record: `docs/kml-kmz-input-consolidation/kml-kmz-input-consolidation-open-questions.md`

If this runbook conflicts with `docs/kml-kmz-input-consolidation/kml-kmz-input-consolidation-implementation-plan.md`, the authoritative plan wins.

## 1. Execution Policy

- Do not implement KML/KMZ input consolidation in one uninterrupted pass.
- Implement in grouped runs with mandatory stop points.
- Do not begin a downstream run until all commands, gates, and file-scope checks for the current run pass.
- Passing agent-verifiable gates do not require human approval by default.
- Gate results are evaluated from command output, file-scope checks, stated continue gates, and documented validation evidence.
- If the user asks for full implementation, the agent should continue from one passing run to the next without waiting for approval, while still reporting the run summary.
- Do not stop for human approval merely because a run completed, tests passed, files changed within the allow-list, or manual validation can be performed by the agent.
- Human review blocks progress only under the conditions in section 3.
- If a gate fails, patch only files allowed for the current run or revise the authoritative plan before touching additional files.
- Keep JPG functionality intact. JPG improvements are paused, not removed.
- Keep `test_data/` read-only.
- Keep `.gitignore` configured so `test_data/` is ignored; `git status --short` must not list sample data files or folders.
- Treat the user-supplied `A:\...` North 2 sample inputs as read-only validation inputs.
- Do not write generated validation files into `test_data/`, `outputs/`, source sample folders, the `A:\...` sample folder, or the Buffer-Zone-Generator repo.
- Use temporary directories for automated and manual validation outputs unless the user explicitly chooses a persistent output location.
- Run Python validation commands without writing bytecode into the worktree. Use `python -B` for unit tests and the in-memory source compile command below instead of `python -m compileall`.
- If a command creates or modifies `__pycache__/` or `.pyc` files, treat that as a gate issue: remove untracked generated bytecode, restore only bytecode files modified by the current validation run, and rerun with the bytecode-free commands.
- Do not launch, attach to, automate, close, kill, inspect, script, or otherwise interact with any Agisoft Metashape process, window, project, task queue, or processing job.
- Do not read from, write to, copy, move, delete, lock, or otherwise touch Metashape project artifacts, including `.psx`, `.psz`, and `.files` project directories.
- No run, required command, manual check, validation step, or close gate requires opening or controlling Metashape.
- Do not shell out to, import from, or modify `C:\Users\rbake\Desktop\VS Code Shortcuts\Buffer-Zone-Generator`. It is reference material only.
- Generated manual-validation KMZs are disposable and must not be committed.
- Preview pan/zoom inspection controls are a future follow-up and must not be implemented or used as a gate in this KML/KMZ consolidation runbook.
- If `src/jpg_boundary_kmz_gui.py` is already dirty from the prior preview legend placement fix, record it as pre-existing, preserve it, and do not count it as a current-run change until Run 5 intentionally works in GUI scope.
- After every run, report changed files, commands run, pass/fail status, and next recommended action.
- Every run must include both `git status --short` and `git diff --name-only` in its file-scope check, because `git diff --name-only` does not show untracked files.
- Pre-existing unrelated `outputs/` deletions noted in the authoritative plan must not be restored, deleted again, staged, or otherwise touched.

## 2. Run Report And Continuation Policy

At the end of every run, provide:

- Run number and phases completed.
- Files changed.
- Tests and commands run.
- Pass/fail result for each command.
- Any failures fixed during the run.
- Any remaining risks or observations.
- Whether the next run is safe to start.

Continuation rules:

- If the current run passes and no human-blocking condition exists, the agent can proceed to the next run without waiting for user approval when the user has requested implementation to continue.
- Agent-performed manual validation does not require human approval unless the output is visually or semantically ambiguous under section 3.
- If the current run passes but the user requested only that run, stop after reporting.
- If the current run fails, do not proceed until the failure is fixed within the current run's allow-list or the authoritative plan is revised.

## 3. Human-Blocking Conditions

Human review or approval is required only when at least one condition below occurs:

- A required command fails and fixing it requires touching files outside the current run's allow-list.
- The implementation needs to revise the authoritative plan, file allow-list, product decisions, phase gates, or run grouping.
- Real-sample output has a good metric match but looks visually wrong for orthomosaic crop usage.
- The natural splitter cannot satisfy both the selected direction and the 20 percent area tolerance on the North 2 validation sample.
- Disconnected source linework requires support beyond the resolved first-implementation rejection behavior.
- The agent cannot verify GUI launch or GUI behavior from the available environment.
- The implementation would modify `test_data/` contents, remove `.gitignore` protection for `test_data/`, modify `outputs/`, modify launcher files, modify `agent_prompt_templates/`, modify the `A:\...` source sample folder, or modify files in `Buffer-Zone-Generator`.
- The implementation or validation would launch, inspect, attach to, script, interrupt, or otherwise interact with an active Metashape instance, Metashape project artifact, task queue, or processing job.
- A generated result preserves or exports source linework despite the resolved first-implementation decision not to preserve it.
- A generated result exports interior rings/holes instead of exterior-only polygons.
- A manual output must be written to a user-selected persistent location or overwrite an existing user file.

No human review is required for:

- Passing unit tests.
- Passing the in-memory source compile command.
- Passing GUI smoke verification when the environment supports it.
- File-scope checks where `git diff --name-only` is allow-listed.
- Implementing the fixed KMZ-only export rule.
- Implementing the fixed exterior-only rule.
- Implementing the resolved mixed-file behavior where LineStrings win and polygons are ignored with metadata.
- Implementing the resolved disconnected-output rejection behavior.
- Implementing positive-buffer enforcement for LineString inputs.
- Implementing the split direction control and preview cache invalidation.
- Creating disposable outputs in a temp directory.
- Updating validation notes with objective command and geometry evidence.
